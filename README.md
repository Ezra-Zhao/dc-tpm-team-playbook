# dc-tpm-team-playbook - proof artifact

## What this is

A design package for standing up a Data Center Infrastructure TPM function:
team charter and RACI, a hiring scorecard and interview loop, a program
review operating pack (status / risk / decision), and a 30-60-90 build-out
plan written from a founding-manager perspective.

It was built against the Anthropic Technical Program Manager, Data Center
Infrastructure job description, whose first responsibility is to manage and
develop the DC infrastructure TPM team and hire and build out the function.

## Honest boundary - read this first

**This package mitigates a narrative gap; it does not remove a hard
requirement.** The candidate has never managed a TPM or program management
team, and nothing in this package claims otherwise:

- Every document here is a **design artifact** - written now, by the
  candidate, to show how he would build and run the function. None of it is
  a record of a team he has hired, managed, or reviewed.
- The hiring scorecard and interview loop in particular are **designs, not
  used hiring records**. They were not used to hire anyone.
- The filled program review example uses one fictional project (Project
  Helios, the same invented project as the dc-delivery-playbook) and is
  labelled fictional wherever it appears. No real project, employer, or
  colleague is described.
- Real experience this package is allowed to cite, stated as fact only:
  managing a 20-person engineering team (Vtron, 2017-2019, education
  technology - engineers, not TPMs); onboarding and mentoring new hires in
  data center operations (Asiacom); setting build standards executed by a
  multilingual factory workforce (Quanta). Managing engineers is not
  managing TPMs, and the package says so wherever the distinction matters.

What it proves: the candidate can design how a TPM function should be
chartered, hired, and run, and can discuss that design in operational
detail. What it does not prove: that he has done it with TPMs before. In an
interview, the honest sentence is the opening one - "I have not managed
TPMs; here is the team I would build and the order I would build it in" -
and this package is the evidence behind the second clause.

## Increment vs existing proof artifacts (zero overlap statement)

- dc-delivery-playbook proves the candidate can run a **project's**
  delivery system (schedule, risk, decisions, turnover).
- commissioning-gate-kit proves he can define **acceptance gates**.
- This package is about the **organization layer**: designing the team that
  runs those systems. New surface, no copied content; Project Helios is
  reused only as the shared fictional example project so the packages can
  be read together.
